# Unlist v1.0.0-rc1: specification

Status: locked for building, 2026-11-26.
Source of every decision: the wayfinder map, https://github.com/Hjiaky/Unlist/issues/1, and the ticket each section links. Where this spec and a ticket disagree, the ticket's latest comment wins and this file gets fixed.
Vocabulary: `GLOSSARY.md`. Principles and working rules: `AGENTS.md`. Architecture: `docs/adr/`.

## 1. What Unlist is

A self-hosted app with which one **Operator** helps the members of their household (the **Subjects**) find out which **Organizations** hold their personal data and get it removed under the GDPR and UK GDPR. It does this with the Subjects' own mail and their own legal rights. It is not a service, not legal advice, and never acts without the Operator's approval.

The core loop: **import mail → discover Organizations → send requests → track each Case → re-check**. Beyond that, the RC contains exactly three extras: a statistics dashboard, Complaint drafts and a breach check.

Out of scope for the RC: see the map's "Out of scope" section. Among others: US web-form opt-outs, multi-user accounts, notifications, OAuth, unsubscribe and account deletion, the username check, the privacy policy watcher, an exposure score, the paid breach lookup, automatic list updates, and templates beyond English and German.

## 2. Principles that constrain every part

From `AGENTS.md` ([decided here](https://github.com/Hjiaky/Unlist/issues/22)):

- AGPL-3.0-or-later; every dependency and bundled data file free and AGPL-compatible.
- One container, one SQLite file, no extra services.
- Works with no configuration beyond adding a Subject and importing mail.
- **The instance contacts nobody unless the Operator turned that on.** No telemetry, no CDNs, no runtime fetching of lists, suffix data or holidays.
- **Every email that leaves in a Subject's name is approved by the Operator first.** The scheduler only prepares.
- Gentle first: polite request, then a reminder, then a Complaint draft. Never threats or compensation demands.
- No nagging, streaks or scores.
- Proprietary online services are optional, off by default and labelled as nonfree.
- The Operator is fully trusted by the Subjects. Privacy rules concern what leaves the instance and what is kept at all.

## 3. Stack

[ADR 0001](../adr/0001-python-django-sqlite.md) and [stack ticket](https://github.com/Hjiaky/Unlist/issues/3).

- Python + Django, SQLite (WAL) through the ORM and migrations.
- Server-rendered templates plus htmx served from the instance. No build step, no web fonts.
- Mail through the standard library only: `mailbox`, `email`, `imaplib`, `smtplib`.
- gunicorn and a `manage.py run_scheduler` loop, started by one entrypoint in one container.
- Bundled data, refreshed only with releases: the Public Suffix List (unmodified `.dat`, MPL-2.0), the holiday calendar, the official Organization List snapshot, and the breach catalogue snapshot.
- New dependencies need an AGPL-compatible licence and a reason the standard library or Django cannot do the job.

## 4. Domain model

Terms as in `GLOSSARY.md`.

### Operator
One login account. Created at first start. Password reset only by a command inside the container.

### Subject
[Authorization ticket](https://github.com/Hjiaky/Unlist/issues/13).

- Name.
- Country of residence, which picks the Supervisory Authority for Complaints.
- Email addresses.
- Mail mode per mailbox: import only, or live connection.
- Identifying details that Organizations commonly ask for: customer numbers per Organization, previous addresses, date of birth.
- Year of birth, and who holds parental responsibility, for children.
- **Consent record:** who consented (the Subject, or a parent for a child), when, and the scope: import mail, send Access and Removal Requests from their address, read and store replies, draft Complaints. It can be withdrawn; open Cases then stop.
- Children from age 12 are flagged as needing their own involvement.
- **Deleting a Subject** erases their Cases, replies, attachments, discovery results, details, consent record and credentials, after one confirmation.

### Organization
[Organization ticket](https://github.com/Hjiaky/Unlist/issues/11). One record per controller, meaning the legal entity that must answer requests.

**Shared fields** (from Organization Lists, overridable locally):

- permanent slug, name, brands (`runs`), domains (registrable domains)
- contacts: privacy email, postal address, web form, phone, preferred channel
- quirks: identification fields it asks for, whether it demands an ID document, request language, notes, template overrides
- relevant countries, Supervisory Authority, categories
- Broker flag, re-check default, last checked date
- quality: verified, tested or scraped

**Local only:** everything about this household's Cases.

**Rules:**

- Scraped (unverified) records are usable but flagged. The Operator confirms the contact before the first request.
- An Organization reachable only by web form or letter is handled like import-only mode: the step is handed to the Subject.
- An Organization on no list becomes a local stub. Nothing is sent until its contact is confirmed.
- Obsolete records with a redirect carry their open Cases over, keeping history and running deadlines.

### Organization List
[Format ticket](https://github.com/Hjiaky/Unlist/issues/15), [domains ticket](https://github.com/Hjiaky/Unlist/issues/30), [official list ticket](https://github.com/Hjiaky/Unlist/issues/31).

- **Format:** one JSON file with a header (name, licence, homepage, version, date, schema version) and its records. Validated against a published JSON Schema; invalid records are skipped with a note, and the previous version is kept.
- **Bundled lists:** the official CC0 list (`organizations.json`) and the JustDeleteMe domain list (`jdm-domains.json`, MIT, a separate file with its notice).
- **Updates:** manual only, through an "update lists" button. The settings page shows each list's date.
- **Merging:** the Operator orders the lists. Per field, the highest list with a value wins, and local overrides beat every list. Records are matched by slug or by a shared domain. Conflicts are shown.
- **Domain conflicts:** a domain claimed by two Organizations matches neither until it is resolved locally.
- **Contact review:** an update that changes the contact of an Organization with a Case applies only after the Operator accepts it, shown side by side.
- **Contributing:** a local override can be exported as a ready-made suggestion for the right repo.

### Case
[Lifecycle ticket](https://github.com/Hjiaky/Unlist/issues/4); reference implementation in the pure `UnlistCase` module in `docs/prototypes/request-lifecycle.html`. A Case is one Subject at one Organization.

**States:**

| State | Next actor |
|---|---|
| found | Operator pursues or ignores |
| draft awaiting approval | Operator |
| handed over (import-only, web form or letter) | Subject sends, then marks sent |
| waiting (clock running) | Organization |
| paused (ID or details asked) | Subject answers or pushes back |
| overdue | reminder first, then a Complaint draft |
| undeliverable (bounce; the clock never started) | Operator fixes the contact |
| Listing found | Subject removes or keeps |
| refused or partly done (exception recorded) | Subject accepts, asks to reconsider, or drafts a Complaint |
| Complaint draft, then Complaint lodged | Subject |
| resting until re-check | nobody until the re-check date |
| closed | nobody (can be reopened) |

**Rules:**

- **Ask, then delete, by default.** A Case starts with an Access Request. A Removal Request follows once a Listing is known. The Operator may choose "request removal directly" for one Case.
- **Approval.** Every outgoing email is approved by the Operator. In live mode, approving sends it. In import-only mode, approving hands it over and the clock starts when the Subject marks it sent.
- **Gentle first.** Silence leads to a reminder and then a Complaint draft. A refusal may go straight to a Complaint draft.
- **Late answers** still move a Case on, even after a Complaint has been lodged.
- **After "nothing held":** Brokers rest until a re-check; others close. Both can be overridden per Organization or per Case.
- **Brokers:** a Removal Request to a Broker asks for a Suppression Record, and the result records whether one was confirmed.
- **History:** every event is stored with its date, including every date that moved a deadline.

## 5. Mail in: import and discovery

[Discovery ticket](https://github.com/Hjiaky/Unlist/issues/12) (with its correction), research in `docs/research/mailbox-discovery-signals.md`.

### Input
- `.mbox` upload (including Google Takeout), or an optional live read-only IMAP connection with an app password. No OAuth.
- IMAP uses `EXAMINE` and `BODY.PEEK[HEADER.FIELDS]`, never marks anything read, and remembers `UIDVALIDITY` and the highest UID seen.

### Identity
- The registrable domain (Public Suffix List) of `From:`, counted only with a DMARC pass or an aligned DKIM result in the provider's `Authentication-Results`.
- Mail that fails this is ignored for discovery.
- Shared platform and email-service domains (the "ambiguous domains" list) are flagged for the Operator to assign.

### Mapping and evidence
- The domain maps through the merged lists (domains, then brands), or to a local stub.
- Evidence grades, strongest first:
  1. schema.org order or booking markup
  2. order, receipt, invoice and shipping mail
  3. welcome, verification, password-reset, security and policy notices
  4. newsletters and other bulk mail
- Bulk is detected by `List-*`, `Precedence` and `Auto-Submitted` headers; kinds by subject and sender keyword rules.
- An LLM, if set up, may suggest a kind only for mail the rules leave unsorted.
- Personal mail (no bulk markers, personal-mailbox domains) is skipped.

### What is kept
- Per Organization and Subject: name, domain, first and last seen, number of emails, evidence kind, and the subject line of the strongest evidence email.
- Bodies are read only for markup and keyword rules, then discarded.

### Operator actions
- A discovery list per Subject, sorted by evidence, with each Organization marked new, already a Case, or ignored.
- "Pursue" (one at a time, or all with account evidence) opens a Case and drafts an Access Request.
- "Ignore" persists across later scans.
- Re-scans are started by the Operator. Scheduled re-scans only for live connections, and only if the Operator switched them on.

## 6. Mail out: drafting, approval, sending

[Templates ticket](https://github.com/Hjiaky/Unlist/issues/27), research in `docs/research/gdpr-request-requirements.md`.

### Templates
- Plain-text files with named placeholders, adapted from the CC0 templates in `datenanfragen/data`.
- English and German in the RC. Other request languages get English; an LLM may offer a translation as a suggestion.
- Locally overridable.

### Every request contains
- the Subject's name and known address, plus only the identifiers that Organization is known to ask for
- a reference code in the subject line (for example `[Ref U-7KQ3]`)
- GDPR or UK GDPR citations, by the Organization's Supervisory Authority
- the one-month deadline
- no reasons, threats or compensation demands

### The templates
- **Access Request:** confirmation and a copy, every Art. 15(1) item, the source and named recipients spelled out.
- **Removal Request:**
  - erasure on the fitting Art. 17 grounds
  - Art. 21(2) objection, plus an Art. 21(1) grounds slot that is left out if empty
  - withdrawal of consent and account closure
  - notification of recipients and a list of them (Art. 19)
  - a Suppression Record request for Brokers
- **Reminder:** names the original request, its reference code and the passed deadline, and gives 14 days.
- **Details reply:** exactly what was asked.
- **ID pushback:** a known address plus proportionality (Art. 12(6), EDPB 01/2022 paras. 73-75); offers details in place of ID.
- **Reconsider:** asks the Organization to name the exact legal duty, and to erase whatever it does not cover.
- **Authority letter:** dated and specific to one Organization; signed by the Subject; never reused.

### Sending
- Live mode: SMTP from the Subject's own address, keeping the Message-ID and the full sent message as evidence.
- Import-only mode: an `.eml` download or `mailto:` link; the Subject sends it and marks it sent.
- Web-form or letter Organizations: the form link or printable letter text, then "mark sent".
- Every approve button shows the exact recipient and whether Unlist sends it or hands it over.

## 7. Replies

[Matching ticket](https://github.com/Hjiaky/Unlist/issues/16), [ID ticket](https://github.com/Hjiaky/Unlist/issues/17).

### Matching, in order
1. `In-Reply-To` / `References`
2. the reference code in the subject line
3. an authenticated sender domain of an Organization with exactly one open Case for that Subject
4. otherwise the unmatched queue

Only matched mail is taken in.

### Outcomes
- Bounces (delivery status notifications) set the Case to undeliverable automatically.
- Auto-replies are attached without a state change.
- Every other outcome is suggested (by keyword rules, or the LLM if set up) and confirmed by the Operator: data found, nothing held, ID or details asked, extension, refused (with the exception recorded), removed (with or without a Suppression Record).

### Storage
Replies and attachments are stored as evidence and readable by the Operator.

### Import-only
The Operator marks the outcome and may attach the `.eml`. Replies found in a later import are matched and offered.

### ID demands
- A details request is answered from the Subject's stored details.
- An ID-document demand gets the pushback first.
- **Unlist never stores ID documents.** If the Subject decides to send one, it is attached from their own device, with redaction guidance (EDPB para. 76). Unlist records only that ID was sent, and when.
- Persistent demands lead to the Subject's choice: send ID, or draft a Complaint.
- Portal-only demands are handed to the Subject.

## 8. Deadlines and re-checks

[Deadline ticket](https://github.com/Hjiaky/Unlist/issues/28), [re-check ticket](https://github.com/Hjiaky/Unlist/issues/18).

### Deadlines
- **Clock start:** the send date.
- **Due date:** the same day-number next month, falling back to the last day of the month, then the next working day by the Organization's country (bundled holidays; weekends only when the country is unknown).
- **UK or EU rules** follow the Organization's Supervisory Authority.
- **Extension:** plus two months, only if announced within the first month with reasons. Otherwise it is recorded and ignored.
- **ID or details asked:**
  - EU: pause from the ask until the answer is sent.
  - UK: a fresh month from the answer.
- **Clarification of a broad Access Request:**
  - EU: pause.
  - UK: the days from ask to answer, both inclusive, do not count.
- **Grace:** overdue 3 days after the due date. A reminder gives 14 days. Both are fixed.

### Re-checks
- A re-check is a fresh Access Request, prepared when due and waiting for approval.
- **Intervals:**
  - Brokers: 90 days after "removed" or "nothing held".
  - Others: 365 days after "removed".
  - None after "nothing held" for non-Brokers, "kept by choice", or an accepted refusal of access.
  - Overridable per Organization or Case.
- Never earlier than the interval, unless the previous answer was incomplete (a reminder) or the Operator asks with a reason.
- Fresh mail from a resting Organization in a new import suggests an early re-check.
- A returned Listing reopens the Case. If a Suppression Record was confirmed, the Subject may go straight to a Complaint draft.

### Scheduler
`run_scheduler` marks overdue Cases, prepares due re-checks and reminder suggestions, and runs opt-in IMAP re-scans. It never sends.

## 9. Complaints

[Complaint ticket](https://github.com/Hjiaky/Unlist/issues/32).

- **Offered:** after a missed deadline plus a reminder, after a refusal, or after persistent ID demands. Never before the request was sent.
- **Addressed to** the Subject's own Supervisory Authority, from the 57 authority records in the seed data.
- **UK Subjects:** first offered a short complaint to the Organization (DPA 2018 s.164A), which they can skip. The regulator draft follows after the answer, or after 30 days without one.
- **Contents:**
  - the Subject's details
  - the Organization's identity and contacts
  - a dated timeline from the Case history
  - the infringement in plain words
  - the remedy sought
  - prior contact
  - attachments: the sent request with headers, the reminder, and the replies
- Satisfies Reg. 2025/2518 Art. 4 for EU cross-border complaints from 2 April 2027.
- **Unlist never submits.** It shows the authority's channel, gives the text or a PDF, and the Subject marks it lodged.

## 10. Breach check

[Breach ticket](https://github.com/Hjiaky/Unlist/issues/33), research in `docs/research/hibp-api-terms.md`.

- Have I Been Pwned's free breach catalogue: a bundled snapshot, a separate CC BY 4.0 file. A manual "update breach list" button fetches `/api/v3/breaches` with an honest `User-Agent`.
- **Matching:** a breach matches when its `Domain` is one of an Organization's domains. Breaches without a domain can be assigned by hand by breach name. Spam lists and malware entries are left out.
- **Per Subject:** breaches at Organizations they deal with, showing the title, date and data classes, and whether the breach falls within first and last seen. One click advances the Case.
- **What it is not:** it does not claim the Subject's own address was in the breach.
- **Attribution** wherever breach data appears: "Breach data from Have I Been Pwned (haveibeenpwned.com), CC BY 4.0", plus each breach's own `Attribution` field.

## 11. Statistics

[Statistics ticket](https://github.com/Hjiaky/Unlist/issues/19).

- **Per Subject and household:**
  - Organizations by evidence kind, and how many are Brokers
  - Cases by state
  - outcomes, including Suppression Records confirmed
  - a monthly chart of Organizations holding data versus removed, recorded from day one

## 12. Optional LLM

[LLM ticket](https://github.com/Hjiaky/Unlist/issues/10).

- **Endpoint:** one OpenAI-compatible endpoint, with no vendor SDKs, and one switch for local versus remote. A remote endpoint shows a one-time notice listing what it will receive and is labelled as a nonfree service.
- **Jobs**, each with a non-LLM fallback:
  - sort leftover discovery mail (sends sender and subject only)
  - translate or adapt drafts (sends template and language, never the Subject's details)
  - suggest reply outcomes (sends the reply text)
  - find a privacy contact (sends the public policy page)
- **Output** is always a suggestion, marked with its source. It changes no state and sends nothing.

## 14. Security, storage, backup

[Security ticket](https://github.com/Hjiaky/Unlist/issues/9), [backup ticket](https://github.com/Hjiaky/Unlist/issues/36).

### Security
- Django authentication, sessions and CSRF protection. Rate-limited login. Secure cookies and strict security headers.
- Listens on the local network by default. Exposed access goes through the Operator's own HTTPS reverse proxy.
- **Encrypted at rest:** IMAP/SMTP app passwords and the LLM key, with a key the Operator supplies by file or environment variable. Everything else is readable in SQLite.
- **Never stored:** mail bodies from discovery, ID documents.

### Backup and restore
- **Backup:** `manage.py backup`, or the settings button, writes one archive: an online SQLite backup plus the attachments folder. The key is not included.
- **Restore:** `manage.py restore` into an empty instance only. It runs migrations, checks integrity, and asks for re-entry of credentials if the key is missing.
- The settings page shows the date of the last backup, with no reminders.

## 16. Official Organization List (separate repo)

[Official list ticket](https://github.com/Hjiaky/Unlist/issues/31), Broker research in `docs/research/eu-uk-brokers.md`.

- **Repo:** `hjiaky/unlist-organizations`, CC0. It holds:
  - `organizations/<slug>.json` (Unlist's fields)
  - `brokers/` (Unlist-only records)
  - `ambiguous-domains.json`
  - `schema.json`
  - a standard-library Python build
- **The build:**
  - overlays a pinned `datenanfragen/data` commit
  - validates against the schema
  - fails on duplicate domains
  - flags named-person contact addresses (published without the email until fixed)
  - carries over obsolete redirects
  - writes `organizations.json` (CC0) and `jdm-domains.json` (MIT)
- **Upstream bumps** are reviewed by diff. Contributions come as pull requests with sources; upstream fixes go to datarequests.org.
- **Brokers for the RC:**
  - flag the 54 already upstream
  - add the 21 new ones, minus ceased rows
  - confirm every `[S]` contact on the Broker's own page first
  - the seven borderline rows need a call
- Each Unlist release bundles a tagged snapshot.

## 17. Release criteria for v1.0.0-rc1

From the [RC ticket](https://github.com/Hjiaky/Unlist/issues/26).

1. The core loop and the three extras work end to end in both mail modes.
2. CI tests cover:
   - the Case lifecycle (from `UnlistCase`)
   - deadline arithmetic (EU, UK, holidays)
   - discovery rules
   - reply matching
   - list merging
3. A container image and compose file; a fresh install reaches first run; upgrades migrate without loss, and this is tested.
4. Docs: install, first run, backup and restore, the optional live connection and LLM, and "what Unlist does and does not do legally".
5. Every obligation in section 15.
6. At least four weeks of real use by one real household with real requests. Findings are fixed or ticketed.
7. The open mailbox questions in [the mailbox test ticket](https://github.com/Hjiaky/Unlist/issues/25) are settled, mostly during step 6.
